# Bot ↔ Table sync oracle — live walk 2026-09-24

Scope: Good Goblin table (`session/server`, `session/client`) vs. the Discord bot (`bot/src`) mirroring it, for a DM + 2 human + 3 headless players on Goblin Warren. Every claim below is cited to the code that makes it true today; "dropped" always names the line that drops it.

Key wire fact used throughout: every module write (`fog`/`doors`/`tokens`/`rolls`/`triggers`/`initiative`) leaves the server as the *same* frame shape — `{type:'state-update', module, state}`, emitted from one place, `session/server/src/modules/registry.ts:178`. The module name is the only thing that tells two events apart; the frame never carries an action verb. `packages/core/src/shared/protocol.ts:44-60` is the full wire type.

## 4. Known gaps going in

- **Token moves/claims never sync at all.** `packages/mechanics/src/tokens/module.ts` never calls `logged()`, and `bot/src/goblin/session-log.ts`'s event switch (`:186-208`) has no `case 'tokens'` — it falls through to `default: return []` at `:205-206`. Positions surface exactly once, baked into the recap map PNG at session end (`bot/src/goblin/live-session.ts:416-422`).
- **Fog auto-explore is silent by design.** `packages/mechanics/src/fog/module.ts:362-363` explicitly writes no log line for the token-vision sweep; only a DM's explicit reveal/hide/reset/bulk/open-map/region-set button call is narrated (`fog/module.ts:162-332`).
- **`dm-disconnected`/`dm-reconnected` can never fire for the human DM.** The bot's observer holds a permanent `role:'dm'` seat (`bot/src/goblin/seat.ts:57`, `mintServiceToken(...,'dm')`), so `hasConnectedDm()` (`session/server/src/ws/SessionManager.ts:348-351`) is always true; the guards at `SessionManager.ts:209` (`dmReturning`) and `:247-249` never trip. `bot/src/goblin/session-stats.ts:206-211`'s handlers for those two event types are consequently dead code — the DM's presence is only ever visible through the generic `player-joined`/`player-left` path.
- **`observer.command()` never confirms server acceptance.** It returns `true` once a frame is written to an open, joined socket (`bot/src/goblin/observer.ts:348-363`); the server's `error` reply (protocol-mismatch aside) is never awaited or surfaced to the caller (`observer.ts:211-212`, `:314-322`). `/roll` doesn't even check the boolean (`bot/src/bot/command-registry.ts:565-573`).
- **Journal card images are dropped.** `WireJournalEntry.imageKeys` (`bot/src/goblin/observer.ts:107`) is declared but never read; `journalLine()` (`bot/src/goblin/session-log.ts:78-84`) only emits `title`/`body` text.
- **Unrecognized log actions vanish without a trace.** `logSentence()`'s default case (`session-log.ts:111-113`) returns `''` for any door/fog action word this build doesn't know, and `diff()` (`session-log.ts:132-144`) still marks that entry's id "seen" — so it can never be retried or logged as an error.
- **`/note`, `/recall`, `/character *`, `/quests *`, `/campaign settings`, `/campaign status` never touch the game server** — confirmed by grepping `command-registry.ts` for every `deps.goblin.`/`deps.sessionRunner.`/`deps.rest.` call site; none appear near those handlers. They are bot-local SQLite features layered beside the table, not synced with it.
- **`/ping`'s server probe hits a route that doesn't exist.** `GET /api/health` (`bot/src/goblin/rest.ts:117`) has no handler in `session/server/src/http.ts`'s route table (`:76-119`); it always 404s, and `rest.ts:56`'s comment says that's fine because only reachability is being measured.
- **Initiative rosters do not seed from a live snapshot.** A DM's manual `/initiative`-adjacent table action (`initiative:start`) sends an explicit `entries` array built client-side; the only *automatic* seeding path is a fired encounter trigger materializing tokens and calling `initiative:seed` internally (`session/server/src/triggers/prepResolver.ts:96-116`), which is not reachable from any socket (absent from `initiative/module.ts:66-81`'s `commands` map).
- **`/map` is confirmed removed** — no such command exists in `bot/src/bot/commands.ts`, and no `/encounter`-style command has ever been added.

## 5. Root causes (walk 1)

Evidence pulled from `bot/check-live/out/cp-*.json` (read-only, captured live 2026-09-24 08:44–09:00 UTC). `discord.board.text` is byte-identical (359 chars) across every checkpoint from `cp-p0-seated` to `cp-s3-door`; the checkpoint schema doesn't capture `edited_timestamp`, so whether Discord's edit endpoint actually fired each time is unrecorded either way. `bot.stats.doorsOpened` reads `0,0,0,1,1,1,1,2` across the eight `cp-*` checkpoints in order; `discord.thread` shows the DM opened **Old Gate** then **Timber Door** (two distinct doors) inside the same `p3-doors` phase, yet the counter only advanced by 1 there — then a *third* open (Old Gate again, at `s3-door`) advanced it correctly to 2.

### 1. Live board counters never move — by design, not a throttle bug
`liveSessionBoard()` (`bot/src/features/session.ts:43-69`) never renders `doorsOpened` or `scenes` at all — its blocks are only the roster, scene name, calendar line, and DM-connected footer (`session.ts:57-67`). `live-session.ts:311` does call `refresh.call()` on every non-`session-ended` event, throttled to one edit per `EMBED_EDIT_MS` (5s, `live-session.ts:36,177-187`), so `deps.edit()` genuinely re-fires — it just re-renders the same bytes because none of the fields the board *does* show (5-player roster, "Goblin Warren", DM connected) changed all walk. Not a bug in the Components V2 redesign (`card.ts`/`ui.ts` just render whatever blocks they're given). **Fix:** add a `Doors opened · N` / `Scenes · N` block to `liveSessionBoard()`, sourced from `stats.recap(Date.now())` the same way `countersOf()` (`live-session.ts:532-535`) already does. **Bot code.**

### 2. `doorsOpened` undercounts a scene's *first-ever* door touch
Root cause in `countOpens()`, `bot/src/goblin/session-stats.ts:164-176`. `resync()` (`session-stats.ts:142-162`) sets `openDoors = hasByScene(state.modules?.doors) ? snapshotOf(...) : null` (line 158); `hasByScene()` (`:234-236`) returns `true` for the module's untouched `initialState` (`{byScene:{}}`), so the baseline becomes `{}` (a defined-but-empty object), not `null`. The very first door anyone opens in a fresh scene seeds the *whole* scene (`doorsOfScene`, `packages/mechanics/src/doors/types.ts:86-95`) and broadcasts the full state — but `openDoors['scene']?.['doorA']` reads `undefined` against that empty baseline, and line 171's check `=== false` is strict: `undefined === false` is `false`, so the transition is silently never counted. The scene's *second* door touched (already present in the baseline the first door's own broadcast established) counts correctly — exactly the observed 0→1 (should be 2) then 1→2 pattern: Old Gate's open was dropped, Timber Door's open counted, Old Gate's later reopen counted. **Fix:** in `countOpens`, change the comparison at line 171 to `openDoors[sceneId]?.[doorId] !== true` (treat "absent from the baseline" the same as "known closed") instead of `=== false`. **Bot code.**

### 3. DM narration in the Log box always renders with the dice emoji
`rollLine()` (`bot/src/goblin/session-log.ts:55-67`) unconditionally opens every `WireRollEvent` with `🎲 **${who}**` (line 57), regardless of whether the event carries a formula, breakdown, or total. The table's `GameLog.tsx` manual-post field (`session/client/src/components/GameLog.tsx:8,18-21`) calls `usePostRoll()` for *any* typed line — a real roll and free narration ("A scream from the cave mouth.") both travel as a `rolls:post` command producing a `RollEvent` with `source:'manual'` and no `formula`/`total` (`packages/mechanics/src/rolls/types.ts:6-34`, `41-42`). That's correct, by-design client behavior — a single free-text box is the product. The bot's `WireRollEvent` type (`bot/src/goblin/observer.ts:64-76`) doesn't even re-declare `source`, so `rollLine()` has no discriminator to reach for today. Confirmed live: thread line `🎲 **Sainayan** A scream from the cave mouth.` (checkpoint `cp-s3-door`, `discord.thread` id `1552604632029859886`). **Fix:** in `rollLine()`, only prepend the `🎲` segment when `event.formula` or `event.total !== undefined` is present; otherwise emit a plain `${stamp} **${who}** ${text}` line (no die, no math suffix). **Bot code.**

### 4. Token moves/claims produce nothing in Discord — confirmed, plus the smallest hook set
Confirmed both halves: `packages/mechanics/src/tokens/module.ts` never calls `logged()` anywhere — `put()` (`:229-235`), `move()` (`:378-387`), `claim()` (`:504-508`), and `assign()` (`:525-532`) all call `ctx.setState()` with no `log` field, unlike `doors/module.ts`'s `put()` (`:136-152`) which does. `bot/src/goblin/session-log.ts`'s `fromModules()` (`:161-173`) has no `'tokens'` entry in its `of()` list, and the `apply()` switch (`:185-207`) has no `case 'tokens'` — it falls to `default: return []` (`:205-206`).
Smallest product-worthy line set: (a) **"X entered `<room>`"** on a room *change*, not every move — the fog module already computes a token's room, twice: `session/server/src/fog/autoExplore.ts:34` dispatches `fog.auto-explore` with the rooms a token's own sweep just earned, and `session/client/src/modules/fog/FogRenderer.ts:471-478` (`partyRoomIds`) does the same room lookup client-side for rendering.
