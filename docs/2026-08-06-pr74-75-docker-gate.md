# Docker gate walk — transform controls (#74) + canvas context menus (#75)

**Date:** 2026-08-06
**Commit under test:** `a24f118` (main) — "Give every canvas child a right-click context menu (#75)", on top of `4b7dd0a` "Make the transform gizmo reliable and finish its controls (#74)"
**Artifact:** `map-goblin:pr7475-gate`, container `mg-pr7475-gate`, `http://localhost:8080`
**Verdict:** **Do not ship as-is.** 16 of 18 checklist items pass. Two fail, and one of the failures is a functional breach of a guarantee that shipped in #61. Two P0s block.

## 1. Provenance and method

The build came from a clean checkout, not the working tree — the working tree was on `node-editing` with 18 modified files that are not part of these PRs.

```
git worktree add .claude/worktrees/gate-main main --detach   # → a24f118
docker build --target runtime -t map-goblin:pr7475-gate .    # from that worktree
docker run -d --name mg-pr7475-gate -p 8080:80 map-goblin:pr7475-gate
```

Build was clean: vite emitted only the pre-existing chunk-size and dynamic-import advisories, no errors.

**Isolation.** Docker was empty of running containers at start; every container in `docker ps -a` was exited (hqvgc from 10 days ago, scrypt from 2 weeks, buildx from 2 days). The other workstream's `triggers-runtime-*` containers were already gone. Nothing belonging to another workstream was started, stopped, or removed, and no volume was touched — `triggers-runtime_game-server-data` and `publish-library_game-server-data` were left alone.

**Map.** Authored fresh in this build, per house rule — no recycled fixture. Two rooms with floors and walls, a river, a door in a wall, a text label, two lights, and four props (three manifest-backed, one pack asset, deliberately mixed so the Swap strip had both a positive and a negative case). 12 children across 3 layers. It survived a save/load round trip intact.

**Instrumentation.** `window.__STORE__` is present in production builds (`packages/core/src/store/store.ts:157` is guarded only on `typeof window`), so every assertion below is checked against store state, not against pixels alone. `__pixiApp` and `__store` are dev-only and were not available.

### Environment notes (not defects in these PRs)

- **E1 — a pre-existing map in this browser profile is format v3.1; this build is v3.0.** On first load the app logged a handled *warning* — `Incompatible file version "3.1". This app requires v2.0 or v3.0 format.` — and fell back to an empty editor rather than crashing. That is correct defensive behaviour. The v3.1 data came from another workstream; I did not open it again.
- **E2 — the browser's network capture reports `/packs/index.json` as 503 on every page load.** This is a capture artifact, not a server error. nginx's own logs show that request served as **304**. Across the whole session nginx served **27× 200 and 28× 304, zero 4xx, zero 5xx**, with no entries in the error log.
- **E3 — a backgrounded tab freezes the Pixi render loop.** `requestAnimationFrame` never fires and the canvas silently stops updating while DOM/React continues to work, so screenshots look plausible but stale. The tab must be the *active* tab in a *non-minimized* window. Worth recording for future walks: `document.visibilityState` and a one-second rAF count are the cheap way to detect it before trusting anything visual.

## 3. Defects

### F1 — [P0] Layer lock does not prevent edits through the context menu

Locking a layer disables the *verb* rows (`aria-disabled`, `pointer-events: none`) but leaves four editing paths live, and they are not cosmetically live — they write.

Proven on a layer with `locked: true`:

| Path | Result while locked |
|---|---|
| Swap thumbnail | `assetId` changed `puddle-water-blue-a1` → `puddle-water-muddy-a5` |
| Radius slider | `radius` changed `6 → 11.5` |
| Move to layer ▸ Layer 2 | Child **moved off the locked layer** (Layer 1: 11→10, Layer 2: 0→1) |
| Colour swatches | Enabled, `pointer-events: auto` |

Only the Flicker toggle disables correctly.

**Root cause** — `canvas/src/canvas/menuRegistry.ts:286-294` maps `disabled: true` onto rows matching `'onSelect' in r || r.type === 'toggle' || r.type === 'slider'`, but:
- `MenuSliderRow` (`canvas/src/components/ui/context-menu.tsx:40-52`) has **no `disabled` field**, and the `'slider'` render branch never reads one or forwards it to `SliderInput` — so the flag is set on data that nothing consumes.
- Swatches and thumbnails expose `onPick`, not `onSelect`, so the `.map` skips them entirely; neither row type has a `disabled` field either.
- The map does not recurse into `r.rows`, so submenu children are never flagged.

The unit test at `canvas/src/canvas/menuRegistry.test.ts:116` asserts only `if ('onSelect' in r)`, which is why this passes CI while the gap exists.

This regresses the guarantee shipped in #61 ("Enforce layer lock and visibility across all editing paths"). **Fix:** add `disabled` to the slider/swatches/thumbStrip row types and honour it in each render branch, recurse into submenu rows — or, smaller and harder to re-break, gate the mutation at the single `commitChild` / `updateChild` seam on the layer's locked/hidden state so no future row type can bypass it.

### F2 — [P0] No visible focus indicator anywhere in the new chrome

`focus-visible:ring-3` is not a Tailwind v3 utility. The v3 `ringWidth` scale is `{0, 1, 2, 4, 8, DEFAULT: 3px}` — there is no `3` key, and `canvas/tailwind.config.ts` does not extend it. The class silently emits nothing.

Verified three independent ways:

1. **Shipped CSS** — `grep ring-3` in `/usr/share/nginx/html/assets/index-D7PEMtkX.css` → **0 matches**. The only ring-width utilities that compiled are `.ring`, `.ring-2`, `.focus-visible\:ring-1`. The *colour* utility `.focus-visible\:ring-border-focus\/50` **did** compile — it sets `--tw-ring-color` and nothing else, which is why this looks correct in the source.
2. **Isolated compile** — running `ring-3` through the project's own config produces zero CSS, while `ring-1/2/4` compile.
3. **Runtime, in the deployed build** — arrow-key onto a menu row, then read computed style:
   ```
   :focus-visible matches → true
   outline: rgba(0, 0, 0, 0) solid 2px      ← Tailwind's outline-none = transparent, not removed
   box-shadow: none                          ← the ring never drew
   --tw-ring-shadow: 0 0 #0000               ← width utility absent
   --tw-ring-color: rgb(145 196 100 / .5)    ← colour utility present
   ```

Because these same elements also carry `focus-visible:outline-none`, the native indicator is suppressed and nothing replaces it. Affected in scope: every context-menu action row, toggle row and submenu row, and all five action-bar buttons. The same typo recurs at `LayerRow.tsx:308,333,354`, `ChildRow.tsx:233,255`, `LayerPanel.tsx:109` and the shared `button.tsx:8` — so it is codebase-wide, not local to these PRs, but these PRs added new instances of it.

The sharp edge: the 20px colour swatches use `focus-visible:ring-1`, which *is* valid — so the decorative dots get a focus ring and the **Delete** row does not.

`docs/chrome-style-guide.md:155` already carries the checklist item this would have caught: *"Focus rings are visible on every interactive element (they compile — check the built CSS, not the source)."*

**Fix:** one line in `canvas/tailwind.config.ts` → `theme.extend.ringWidth = { 3: '3px' }`. Then re-run the guide's own check against the built CSS.

### F3 — [P1] Swap-strip thumbnails are broken images in production

All four thumbnails render with `naturalWidth: 0`. The `<img src>` comes from the manifest's `entry.path` (`/textures/objects/Puddle_Water_Blue_A1_2x2.png`), and those files are **not in the build**: `canvas/public/` contains only `favicon.svg` and `packs/`, and the container has no `/usr/share/nginx/html/textures` directory at all.

nginx's SPA fallback then serves `index.html` for every one of them — **HTTP 200, `content-type: text/html`, 1367 bytes**, which is exactly the size of `dist/index.html`. That is why this fails silently: no 404, no console error, nothing in the network panel that looks wrong.

The props themselves render on canvas because the engine resolves art through the rehydrated asset packs (`127 texture(s)` from IndexedDB), not through `entry.path`. Only the menu's raw `<img src={n.path}>` uses the manifest path.

Behaviourally the strip is correct — picking a thumbnail commits the swap and lands exactly one undo entry — but the user is choosing replacement art from four identical broken-image glyphs, which defeats the feature.

**Fix:** resolve thumbnails through the same pack-aware texture resolver the canvas uses, rather than `entry.path`. Failing that, ship `/textures` or hide the strip when the image cannot resolve.

### F4 — [P1] Gizmo is not created when a child is selected from the Layers panel while the canvas selection is empty

Reproduced twice, isolated by A/B:

1. Click empty canvas to clear the selection (`selectedIds` = `[]`).
2. Click a child row in the Layers panel.
3. The child *is* selected — store, Transform panel and floating action bar all populate — but **no gizmo is drawn**.
4. Clicking the same child on canvas immediately restores the full gizmo.

Selecting a *different* child first (non-empty → non-empty) works fine, which is what makes this easy to miss. A related no-gizmo state was seen once immediately after stamping an asset — same signature, not re-confirmed, likely the same root cause (selection arriving from a non-canvas path out of an empty selection).

Net effect: the user has a selected object, a visible action bar, and no way to scale or rotate it until they click it again on the canvas.

### F5 — [P1] Two contradictory W×H readings for one rotated object

Rotate a prop 30°. The gizmo chip reads `15.3 × 14.0 sq` (the rotated axis-aligned bounding box); the Transform panel simultaneously reads `12.5 × 9` (the object's own size). Both are on screen, both labelled W and H.

`SelectTool.ts:513` passes rotation `0` into `gizmo.update()`, so the box never rotates, and line 511 builds the chip from the axis-aligned union. For a measuring tool used to size props against doorways, two authoritative numbers for one object is worse than either being slightly wrong.

**Fix (smallest correct):** when the selection is a single rotated asset or text, build the chip from the child's own size so it matches the panel; keep the AABB only for multi-selection unions, where no single object size exists.

### F6 — [P1] Controls that do nothing

The action bar renders Flip H / Flip V / Rotate 90° for **every** selection, but `flipSelection` skips text and lights and `rotateSelection90` skips lights. Selecting a light and clicking Rotate 90° produces no change, no toast, no disabled state. `buildMultiMenu` has the same problem for mixed selections.

The codebase already knows the right answer — `SelectTool.ts:503` hides the rotate stem for lights precisely so as not to draw an affordance that does nothing. The DOM chrome did not get the same treatment.

**Fix:** derive the action list from the selection's child types and omit inapplicable verbs rather than showing dead ones.

### F7 — [P1] Delete is treated as an ordinary verb in the action bar

In the context menu, Delete gets `separatorBefore`, `danger` styling and a `Del` hint. In the action bar, the same verb is the fifth of five identically-styled 26px buttons at `gap-0.5` (2px), immediately after Duplicate, with `text-text-secondary` — **byte-identical styling to the other four** (`rgb(182,188,179)` computed) — no separator, no danger colour, no confirmation, no undo hint.

Two brand-new surfaces from the same PR pair present the same destructive verb with opposite levels of care. A mis-tap in a dim room deletes a prop with no signal that Ctrl+Z exists.

### F8 — [P2] Four of five canvas overlays ignore the white+ink rule

`packages/core/src/engine/overlayPalette.ts` opens by arguing the rule: overlays are theme-free, white strokes over a near-black ink underlay, "like a camera viewfinder", because a coloured overlay disappears on same-hue art. The gizmo follows it. Nothing else does:

| File | Constant | Value |
|---|---|---|
| `tools/SelectTool.ts:100` | `HOVER_COLOR` | `0x4488ff` (the periwinkle hover rectangle seen on canvas) |
| `tools/SelectTool.ts:73,84` | marquee fill + stroke | `0x4488ff` |
| `shapeNodeOverlay.ts:12` | `OUTLINE_COLOR` | `0x6c63ff` |
| `shapeNodeOverlay.ts:14`, `wallNodeOverlay.ts:19` | `SELECTED_COLOR` | `0xfbbf24` (Tailwind amber-400) |
| `roomHighlight.ts:5` | `HIGHLIGHT_COLOR` | `0x38bdf8` (Tailwind sky-400) |

Stock framework palette values, hardcoded, on hand-painted map art, in a codebase that just wrote the file explaining why that fails. `0x4488ff` and `0x38bdf8` both vanish against blue water. This is also the art-style-guide gate rule ("overlays are white + ink only, never the theme accent"). Differentiate hover from selected by weight and dash, not hue.

### F9 — [P2] Disabled rows fall below the contrast floor, and the whole menu greys out with no explanation

`opacity-50` composited on `surface-1` (night):

| Token | Composited | Ratio |
|---|---|---|
| `text-primary` @50% | `rgb(129 131 128)` | 4.58 (passes, barely) |
| `danger` @50% | `rgb(124 80 73)` | **2.59** |
| `text-muted` @50% | `rgb(88 92 86)` | **2.57** |

Below even the 3:1 non-text floor. This matters more than a normal disabled state because `buildChildMenu` disables *every* row at once on a locked or hidden layer — so the entire menu drops to ~2.6:1 with no text saying why, while the paste path two functions away *does* call `notify.warning('Layer is locked')`. Same condition, two behaviours, and the silent one is the one the user hits first.

For the record, the base token ramp itself is sound — all four text tokens clear 4.5:1 on all four night surfaces (worst case `text-muted` on `surface-3` = 4.66; status-bar `text-muted` on `surface-1` = 6.37; `danger` on `surface-1` = 6.51). These are compositing failures, not token failures.

### F10 — [P2] Swatch selection is encoded by colour alone, below any usable contrast

The active colour swatch is marked only by a 2px `border-accent-active` ring. Against the fills it must read on:

| Swatch | Ratio vs ring |
|---|---|
| `#ffb45e` | 1.16 |
| `#aec8ff` | 1.22 |
| `#ff7a5e` | 1.25 |
| `#ffdd88` | 1.55 |

### F11 — [P2] Assistive-technology gaps in the new menu

- Both range inputs (`Radius`, `Intensity`) have **no accessible name** — the caption is an unassociated sibling `<div>` with no `for`/`aria-labelledby`.
- `role="menu"` contains bare `<button>`s with no role (swatches, thumbnails, trailing button) and bare `<div>` separators — invalid containment, so item counts and Home/End semantics are wrong.
- Door style state is a literal `' ✓'` appended to the label string (`menuRegistry.ts:253`) on a plain `role="menuitem"` — invisible to AT. Two rows above it, `Secret` does the identical job correctly with `role="menuitemcheckbox"` + `aria-checked`. One menu, two answers to one question.
- Swatches announce as raw hex ("hash a e c eight c eight f f").
- The ratio-lock button reads "Unlock aspect ratio" while `aria-pressed={true}` — the name states the action, the state states the opposite.
- Colour swatches are 20×20 and the solo-exit chip is ~20px tall, both under the 24×24 minimum.

### F12 — [P2] Resizing a light also moves it

A corner drag on a light scales `radius` (6→7.5, correct) but also relocates the centre (2,−4) → (3.5,−2.5), because the drag anchors to the opposite corner as it would for a box. For a radial object the expected behaviour is to grow about the centre.

### F13–F18 — [P3]

- **F13** The swap strip is 8 × 36px + gaps ≈ 330px inside a `max-w-[260px]` popover, producing a horizontal scroller *inside a context menu*.
- **F14** `.gg-grain` is `background-image: none` under `.dark`, and night is the default — yet it is applied to both new chrome roots. Dead class in the shipped theme.
- **F15** No `:active` state on any menu row or bar button; zero press feedback. Meanwhile `index.css` carries fifteen bespoke toast-icon animations (200–1000ms, most outside the 150–250ms band). The motion budget is spent on decoration and starved on state.
- **F16** `buildMultiMenu` has no "Move to layer", though every single-selection menu does — and multi-select is where it is most wanted.
- **F17** The status bar's permanent slot shows `FPS` and `frame-ms` and never the map name or save state. When faded (`opacity: 0.4`) its text composites to **2.04:1**. Also, the ruler and the solo pill share one centre slot with the ruler winning — so measuring while soloing hides the only exit-solo control.
- **F18** `settle` is defined but unused in the new chrome; every transition here resolves to Tailwind's default 150ms `cubic-bezier(0.4,0,0.2,1)` instead. `prefers-reduced-motion` **is** correctly honoured by a universal block, including the status bar's inline transition.

## 4. Design critique

*Method: two isolated assessments (design review; deterministic detector + code scan), synthesized here. Every claim that drives a P0 was re-verified by the orchestrator directly against the shipped artifact and the live runtime.*

### Design health — 22/40 (Acceptable: significant improvements needed)

| # | Heuristic | Score | Key issue |
|---|---|---|---|
| 1 | Visibility of system status | 2 | Gizmo silently absent on panel-origin selection (F4); a selected door produces no canvas feedback at all; nothing anywhere shows save state |
| 2 | Match system / real world | 3 | "sq", "Prop", "Label" are the DM's words; swatches announce as raw hex and the status bar speaks engine ("frame-ms") |
| 3 | User control and freedom | 3 | Undo is exemplary — one step per gesture, verified across eight gesture shapes. Docked for unconfirmed Delete and for Escape leaving a field focused |
| 4 | Consistency and standards | 1 | Two "checked" affordances in one menu; two W×H readings for one object; Delete styled two ways; documented overlay rule followed by one of five overlays |
| 5 | Error prevention | 1 | **Layer lock does not prevent edits** (F1); dead controls (F6); destructive verb adjacent to its constructive twin with no confirm |
| 6 | Recognition over recall | 2 | The action bar is five unlabelled icons with `title` only — no text, no shortcut hints, though the menu's equivalent rows all carry them. The bar knows the shortcuts and withholds them |
| 7 | Flexibility and efficiency | 3 | Genuinely strong: contribution registry, full keyboard menu nav with Home/End, kbd hints, the gizmo itself |
| 8 | Aesthetic and minimalist design | 3 | Restrained, correctly dark, right density. Docked for permanent FPS/frame-ms real estate and accent rings on pale swatches |
| 9 | Recognize / recover from errors | 2 | Undo recovers well, but the locked-layer menu greys out entirely with no reason given — while the paste path toasts one |
| 10 | Help and documentation | 2 | `kbd` hints are the only discovery surface; nothing teaches that Left/Right adjusts a focused slider |

### Craft verdict

**Not generic at the bones; generic at the seams.** A user fluent in Linear or Figma trusts the canvas and pauses at the chrome.

The bones are real and were clearly earned. `overlayPalette.ts` reasons from an actual failure mode ("green handles on grass") to the viewfinder answer, and the numbers hold: white-on-ink measures 19.38:1, and against bright parchment where bare white would be 1.36:1 the 0.7-alpha ink underlay composites to 6.35:1. `TransformGizmo.hitTest` *removes* the whole-box move fallback, with a comment naming the trap it replaced — a radius-6 light becoming an unclickable-through region covering half the room. Removing a convenience because it created an invisible trap is a mature call.

The seams are three: an invented affordance (`' ✓'` string-concatenated onto a label, two rows above a real toggle doing the same job), an inconsistent component vocabulary (five overlays, one palette rule, four violations; one Delete verb, two treatments), and dead weight that reads as intentional in source and is nothing in the build (`gg-grain` at night, `ring-3` everywhere).

The deterministic scan found exactly **one** finding — a `broken-image` warning at `AssetBrowserPanel.tsx:71`, which is a **false positive**: that `<img>` has a real dynamic `src` plus an `onError` fallback to `PackThumbnailCanvas`. Notably the detector did *not* catch the two most serious problems here, both of which needed the running build: a class that doesn't compile, and a lock that doesn't lock.

### What's working

1. **The overlay palette is the right solution to a real physics problem, and it is argued rather than asserted.** It is theme-free on purpose, which correctly anticipates the user-customisable accent. Its only flaw is that four sibling overlays never adopted it.
2. **Hit zones are decoupled from visual size** — handles draw at 11px and hit at 20×20 CSS px — and the near-miss fallback was deliberately deleted rather than tuned.
3. **The undo model is coherent across three structurally different input shapes.** Typing commits once on Enter/blur; a slider splits live preview from a single commit carrying the drag-start value; toggles keep the menu open because "a toggle is a setting, not a verb". I verified all three empirically, including the 5-write/1-undo slider drag. Most editors get at least one of these wrong.

### Cognitive load — 5 failures of 8

The light context menu is the acute one: a DM right-clicks a torch to say "dimmer" and gets **12 arrow-key stops** — two sliders, six swatches, a toggle, three verbs and a submenu. Reaching Delete costs eleven ArrowDowns *through two live sliders whose Left/Right keys mutate the map*, so a user who drifts sideways silently changes the lighting. Visual hierarchy also fails: the only thing naming what a slider does is a 10px, 0.1em-tracked, uppercase muted caption — the least prominent element on the row carries the only semantics, which is the worst possible treatment for a word a hurried eye must read in a dim room.

### Persona red flags

**Sam (accessibility-dependent)** — the most damaged. No focus indicator anywhere in the new chrome (F2), and the team's own keyboard-navigation work is invisible because of it. Two unnamed sliders. Invalid `role="menu"` containment. Door style state that AT cannot perceive. A ratio-lock button whose name and state contradict each other. Disabled Delete at 2.59:1.

**Riley (stress tester)** — every probe returns a silent no-op: flip a light, rotate a light, flip a text label, select a door. Lock a layer and the whole menu greys out with no reason — then edit the locked child anyway through a slider. Rotate a prop and get two different sizes.

**The DM mid-session, dim room, players waiting** — the status bar spends its only permanent slot on frame timings and never answers "is my map saved". At `opacity: 0.4` it is unreadable (2.04:1) in exactly the lighting the product was designed for. FPS degradation is signalled by making the number *dimmer* — the moment performance is worst, the warning is faintest. And Delete sits unguarded 2px from Duplicate.

### Questions worth answering

1. **Is the floating action bar chrome or overlay?** Its own comment says "chrome, not canvas overlay — it keeps the theme accent", yet it floats 72px from a gizmo built on an explicitly theme-free palette, on the same pixels, in the same glance. Straddling is what makes it read as pasted on. Either it adopts the viewfinder language, or it docks.
2. **Who is `frame-ms` for?** If the answer is "us", it belongs behind a dev flag and the slot belongs to the map name and save state.
3. **Why is "selected" a raised surface in the layer panel and a 1.2:1 green ring in the context menu?** The chrome already owns a correct, measured answer to "which one is current". Two-thirds of the new menu's state affordances invented worse ones. What made the existing answer feel unavailable here?
