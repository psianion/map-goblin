Token-vision fog — what each phase builds

Mockups + sketches for the plan in docs/2026-08-15-token-vision-fog-plan.md. Panel mockups use the Table's real chrome tokens and component vocabulary; canvas sketches use the map's own palette. Everything here is a proposal for review — nothing is built.

P1

Mechanics + server truth

No visible UI ships. The scene gains mode · rooms/vision, vision share, auto-explore; the server gains the sweep service, the region (grid-bitmask) memory, explore locks, and — the real new secret — token redaction by vision.

P2

The client mask — what a player sees

Vision-mode rendering: current sight is the union of your tokens’ sweep polygons; region memory washes only the cells sight has actually crossed — a half-explored room finally looks half-explored; everything else is void. Feather and the reveal fade carry over.

P3

Light model — ambient, carried light, darkvision

Normal vision sees only what is lit: by the scene’s ambient level, or by a light source — placed, or carried by a token (torch). Darkvision sees unlit space within its own range, desaturated. The DM gets one new dial.

P4

DM controls — everything stays in the DM’s hands

The fog panel grows the mode, auto-explore, vision share and the fog brush; the stubbed token Sight & light section goes live, with sight links; zones gain the explore lock flag. Room list, bulk ops, conceal, undo toasts — unchanged.

P5

Individual vision — per-player worlds

With share set to Individual, each viewer sees through their own claimed tokens only; region memory becomes per-identity and redaction diverges per player. Sight links punch through it where the DM says so.

P6

The gate — proven, not promised

A new e2e spec drives two live browser contexts on the dressed gate map, plus the full unit/wire suites and a Docker + browser walk. The budgets are asserted, not aspirational.
