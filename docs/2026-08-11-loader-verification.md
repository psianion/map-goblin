# Survey loader — verification report

Target: `site/index.html` inline loader (ported from `docs/loader-options/option-a.html`), milestone wiring in `site/src/loadProgress.ts` + `window.__ggMark`.
Tested against the built bundle via `npx vite preview --port 5180` (dist already built). Browser automated via MCP browser tooling, one tab, foregrounded via Windows UI Automation for every measurement (`document.hidden` asserted per reading).

## Overall verdict

**PASS**, with two untested items flagged as CONCERN (both due to tooling limits, not implementation defects) and one informational note (maxScroll baseline is viewport-dependent, not a regression). No console errors beyond the pre-existing, allowed THREE.Clock deprecation warning. No FAILs found.

## Per-check results

1. **Cold load — PASS.** Two hard-reload (Ctrl+Shift+R) runs on 5180: loader visible at first capturable frame, parchment survey styled correctly (no blank/unstyled flash observed within tool latency), phase order followed the design (`raising the walls` → `ready when you are`), total loader lifetime ≈3.2s both runs, exit choreography (ink soak → canvas-mount fade-up → brand/whisper stagger) played cleanly, landing on the lit-table scene. CDP network throttling (Slow 4G) was not reachable — no CDP session/DevTools-protocol tool exposed to this harness — so throttling is untested; substituted with two repeated no-cache (hard-reload) loads instead, per the fallback instruction.
2. **Warm load — PASS (weak differentiation).** Reload with normal cache: progression and phase order identical to cold, MIN_MS floor honored (loader never disappeared before reaching 100%), no phase-skipping glitches. Could not strongly differentiate warm-vs-cold pacing: on localhost, asset transfer time is near-zero even cold, so the pen's pace is dominated by JS eval/shader-compile cost (identical either way), not by network — a limitation of testing against localhost rather than a loader defect.
3. **Exit handoff — PASS.** Post-clear state: `scrollY === 0`; `<html>` attributes reduced to `lang="en" class="lenis" style="--night-t: 0.000;"` (only the app's own token, no `data-gg-loading`/`--gg-*` residue); `#root` has neither `inert` nor `aria-busy`; `.stage-lamp` computed opacity `1`; `.grain` computed opacity `0.12`; `#gg-loader` removed from DOM. Wheel tick (1 tick) moved `scrollY` from 0 to 99 (Lenis momentum) — scroll unlock confirmed working, not regressed. `pin-spacer` count = **9**, matching spec, at every viewport tested. `maxScroll`: measured 9780 at 1584×815 and 8580 at 1424×715 — **not** the ~11004 baseline named in the brief. This tracks the viewport: `scrollHeight − innerHeight` recomputed correctly at each size via the live Lenis instance (`lenis.limit` matches `document.documentElement.scrollHeight − innerHeight` exactly both times), so the number is viewport-dependent, not a broken scroll range; the ~11004 baseline was presumably captured at a different reference viewport this session didn't reproduce. Flagging as informational, not a FAIL — reproduce at the exact original viewport size to confirm exact parity if that number matters as a hard regression gate.
4. **Deep link (`#door`) — PASS.** Cold hard-reload of `http://localhost:5180/#door`: `scrollY` stayed 0 through the whole load (scroll pinned, hash not honored early), then after clear jumped straight to the door section (`getBoundingClientRect().top === 0`, in view) — not to `y=0`. Matches the "anchor honored only at the safe moment" design.
5. **Reduced motion — CONCERN-untested (live), PASS (code review).** Attempted to flip `prefers-reduced-motion` via `SystemParametersInfo(SPI_SETCLIENTAREAANIMATION)` (the Windows-side control Chromium is documented to read); the OS-level flag verifiably flipped (`SPI_GETCLIENTAREAANIMATION` read back `0`) but `matchMedia('(prefers-reduced-motion: reduce)').matches` stayed `false` in the browser after a wait and a fresh navigation — this Chrome/Windows build isn't picking up the live toggle, and no CDP `Emulation.setEmulatedMedia` or DevTools Rendering-panel access was reachable from this harness to force it. Setting was restored to its original value immediately after. Verified instead by reading `dist/index.html`: the `matchMedia(...).matches` branch (lines ~591–609) renders the composed still (`render(1)`), sets phase to "ready when you are", holds for `goal`/`MIN_MS`/`CAP_MS`, then does a flat opacity crossfade (`--gg-a: 0`, 320ms) with no drawing/travel/blur — matches the spec exactly, including the `!important` transition override for the loader/canvas-mount/brand/whisper under the media query. Recommend a manual OS-toggle or CDP-enabled pass before shipping if this gate matters for release sign-off.
6. **Mobile widths — PASS.** Tested ~500px (target 390/430 — Windows DPI/window-chrome meant actual `innerWidth` landed at 500/657 rather than the exact requested CSS px, but both fell under the 700px breakpoint) and 752px (target 768, above breakpoint). Under 700px: cartouche measured strictly below the stage (`cartTop >= stageBottom`), full width, nothing overlapping the corridor — screenshots confirm a clean stacked layout. Above 700px (752px case): cartouche sits in the sheet's bottom-left corner as designed for desktop layout. Breakpoint transition confirmed correct at both sides. Exit choreography re-checked at mobile width — clean, no overlap issues.
7. **A11y probes — PASS.** During load: `#gg-loader` has `role="status" aria-live="polite"`, no `aria-label`; `#gg-plan` (SVG) and `#gg-pct` both `aria-hidden="true"`; `#gg-phase` has no `aria-hidden` (the only announced content, as designed); `#root` has both `inert` and `aria-busy="true"`. After clear: `#root` has neither attribute. Tab key after load moves focus to a real interactive element (`A.cta`) — no focus trap.
8. **No-JS — CONCERN-untested (live), PASS (code review).** Could not disable JavaScript from this harness: `chrome://settings/content/javascript` and other `chrome://` pages are blocked from browser-automation navigation ("Can't interact with browser-internal or unparseable URLs"), and no CDP `Emulation.setScriptExecutionDisabled` was reachable either. Verified instead directly against the built `dist/index.html`: `#gg-loader { display: none; }` is the unconditional default (line ~79), and the only rule that shows it — `html[data-gg-loading] #gg-loader { ... display: grid; ... }` — is gated entirely behind an attribute that is set exclusively by the inline `<script>` (line ~243, `document.documentElement.setAttribute('data-gg-loading', '')`). With JS disabled that script never runs, so the attribute is never set, `#root`'s content (prerendered app) stays fully visible/interactive, and the loader stays `display:none`. Gating logic confirmed correct by source inspection.
9. **Console — PASS.** Across every run (cold ×2, warm, deep-link, mobile ×3): zero errors. One warning present every time, expected and allowed: `THREE.Clock: This module has been deprecated. Please use THREE.Timer instead.` (from `Canvas3D-*.js`).
10. **Impeccable lens (feel) — PASS.** The pen tip genuinely rides the live stroke (`getPointAtLength` following the wall path, not a canned position), and its glow breathes on a clock-driven sine rather than tracking progress — so a stalled milestone reads as "still working," not broken, exactly as the code comments claim. Exit is a single coordinated timeline (cartouche bows out → last torch flare → ink soak → canvas-mount fade-up → brand/whisper stagger) rather than a hard cut; two screenshots taken 300ms apart mid-exit were visually identical with no ghosting, tearing, or misalignment. The survey genuinely dissolves onto the table it was drawn on — reads as the deliberate, non-generic loading treatment the brief asked for. No jank observed in any captured frame on the built bundle.

## Additional note (report only, no fix applied)

Render-blocking CSS (`index-Bi4jYRKg.css`, 4,965 B transferred / gzip of the 23.7 kB source) measured on 5180 via the Navigation/Resource Timing APIs: HTML `responseEnd` at 42.6 ms, CSS `responseEnd` at 115.6 ms (~73 ms after HTML), first paint at 176 ms (~60 ms after the CSS finished, consistent with it being render-blocking). Total delay from HTML arrival to first paint: ~133 ms — small on localhost's near-zero RTT; on a real cold connection this scales with round-trip latency for the CSS request specifically, since the loader's own inline `<style>`/`<script>` don't wait on it but the browser's first paint of anything (including the loader) does. Not fixed per instructions — flagging for awareness only.

## Untested-item summary (for follow-up)

- Slow-4G CDP throttling (check 1): no CDP session tool available in this harness.
- Live reduced-motion emulation (check 5): OS toggle didn't propagate to the browser's `matchMedia`; no CDP emulation available either. Code-verified only.
- Live no-JS disable (check 8): `chrome://` settings pages blocked from browser automation; no CDP script-disable available. Code-verified only.

All three are tooling gaps in this environment, not known defects — worth a manual pass (real DevTools, `prefers-reduced-motion` OS toggle that the browser actually observes, or a CDP-capable harness) before treating them as fully closed.
